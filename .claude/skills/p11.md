# P11 Kubernetes Cluster Operations

Guide for submitting, managing, and debugging distributed GPU training jobs on the P11 Kubernetes cluster.

## Authentication

Credentials expire frequently and must be refreshed before any kubectl or AWS operation.

### Quick auth refresh

```bash
bash ~/verify.sh
```

Run this before any cluster interaction. If it fails or is unavailable, use manual auth below.

### Manual auth

```bash
# 1. Refresh EKS credentials (needed for kubectl)
ada credentials update --provider=conduit \
  --role=SFAI-Project11-EKS-prod-us-west-2-application \
  --account=124355641431 --once --profile EKS-Profile

# 2. Refresh P11 credentials (needed for ECR image push)
ada credentials update --provider=conduit \
  --role=SFAI-Project11-EKS-prod-us-west-2-application \
  --account=124355641431 --once --profile p11

# 3. Update kubeconfig
aws eks update-kubeconfig --region us-west-2 \
  --name SFAI-Project11-500-Prod-EKS-Cluster-prod-us-west-2 \
  --profile EKS-Profile

# 4. Set default namespace
kubectl config set-context --current --namespace=application-nonprod
```

### ECR login (before job submission)

`AWS_PROFILE=p11` must be set before ECR login, otherwise image push fails with authorization errors.

```bash
export AWS_PROFILE=p11
aws ecr get-login-password --region us-west-2 --profile EKS-Profile \
  | docker login --username AWS --password-stdin 124355641431.dkr.ecr.us-west-2.amazonaws.com
```

## Submitting Jobs

Jobs are submitted using torchx from the slime repo root. The `submit_job/submit.sh` script handles authentication, Docker image build, ECR push, and K8s job creation.

### Basic submission

```bash
NUM_NODES=2 EXP_NAME=shuowei-my-experiment bash submit_job/submit.sh
```

### Configurable environment variables

| Variable | Default | Description |
|----------|---------|-------------|
| `EXP_NAME` | `${USER}-slime-router-test` | Job name (becomes pod name prefix) |
| `NUM_NODES` | `2` | Number of nodes (each has 8 GPUs) |
| `IMAGE_TAG` | `slime-feb6` | Base Docker image tag |
| `PRIORITY_CLASS` | `high-priority` | `high-priority` or `low-priority` |
| `TOLERATIONS` | `p11-scheduling/reserved-queue:null` | Queue toleration (see Queue Selection below) |
| `NAMESPACE` | `application-nonprod` | Kubernetes namespace |
| `SERVICE_ACCOUNT` | `application-nonprod-sa` | K8s service account |
| `SCRIPT` | `/shared/dev/${USER}/start_ray_cluster.py` | Entrypoint script on the pod |

### Queue Selection

Jobs can target different queues by changing the toleration in `submit_job/submit.sh`:

- **Reserved queue** (default): `TOLERATIONS="p11-scheduling/reserved-queue:null"`
- **Training engineering queue**: `TOLERATIONS="p11-scheduling/training-engineering-queue:null"`

To use training-engineering-queue capacity, edit `submit_job/submit.sh` line 32:
```bash
# Change from:
TOLERATIONS="p11-scheduling/reserved-queue:null"
# To:
TOLERATIONS="p11-scheduling/training-engineering-queue:null"
```

### What submission does

1. Authenticates to EKS and ECR
2. Builds Docker image via `Dockerfile.torchx` (copies local repo into `/opt/slime/`)
3. Pushes image to ECR (`124355641431.dkr.ecr.us-west-2.amazonaws.com/app/phoenix-rl`)
4. Creates K8s pods running `start_ray_cluster.py` via torchrun
5. Node 0 becomes Ray head, others join as Ray workers

### Pod naming

Pods are named: `{EXP_NAME}-{RANDOM_ID}-startraycluster-{NODE_IDX}-0`

Example with `EXP_NAME=shuowei-my-exp`, 2 nodes:
- `shuowei-my-exp-abc123xyz-startraycluster-0-0` (head node)
- `shuowei-my-exp-abc123xyz-startraycluster-1-0` (worker)

### Submitting multiple independent clusters

```bash
for i in 1 2 3 4; do
  NUM_NODES=2 EXP_NAME=shuowei-my-exp-${i} bash submit_job/submit.sh
done
```

## Pod Management

All commands use namespace `application-nonprod`.

### List pods

```bash
# All your pods
kubectl get pods -n application-nonprod | grep shuowei

# Specific cluster
kubectl get pods -n application-nonprod | grep <cluster-id>

# Wide output (shows node, IP, etc.)
kubectl get pods -n application-nonprod -o wide | grep shuowei
```

### Enter a pod (interactive shell)

```bash
kubectl exec -it -n application-nonprod <pod-name> -- bash
```

### Run a command on a pod

```bash
kubectl exec -n application-nonprod <pod-name> -- <command>
```

### Check GPU usage

```bash
kubectl exec -n application-nonprod <pod-name> -- nvidia-smi
```

### Copy files to/from pods

```bash
# Local to pod
kubectl cp ./local_file <pod-name>:/remote/path -n application-nonprod

# Pod to local
kubectl cp <pod-name>:/remote/path ./local_file -n application-nonprod

# Sync code packages to a pod
kubectl cp ./slime <pod-name>:/opt/slime/slime -n application-nonprod
kubectl cp ./slime_plugins <pod-name>:/opt/slime/slime_plugins -n application-nonprod
```

### Sync code to all pods in a cluster

After making local code changes, push to running pods without resubmitting:

```bash
for i in 0 1; do
  POD="<exp-name>-<cluster-id>-startraycluster-${i}-0"
  kubectl cp ./slime "${POD}:/opt/slime/slime" -n application-nonprod
  kubectl cp ./slime_plugins "${POD}:/opt/slime/slime_plugins" -n application-nonprod
done
```

`PYTHONPATH=/opt/slime` is set in the container, so updated code takes effect immediately.

### Inspect pod issues

```bash
# Pod events (scheduling, OOM, crashes)
kubectl describe pod <pod-name> -n application-nonprod

# Pod logs
kubectl logs <pod-name> -n application-nonprod

# Previous container logs (after a crash restart)
kubectl logs <pod-name> -n application-nonprod --previous
```

## Ray Job Management

Ray commands are executed on the **head node** (startraycluster-0-0). The Ray dashboard runs at `http://127.0.0.1:8265` on the head node.

### Submit a Ray job

From inside the head pod (or via kubectl exec):

```bash
ray job submit --working-dir /opt/slime --address="http://127.0.0.1:8265" \
  --runtime-env-json='{"env_vars": {"NCCL_DEBUG": "INFO", "NCCL_SOCKET_IFNAME": "eth0", "PYTHONPATH": "/root/Megatron-LM/:/opt/slime", "CUDA_DEVICE_MAX_CONNECTIONS": "1"}, "excludes": [".git"]}' \
  -- python3 /opt/slime/train.py <training-args>
```

In practice, use training scripts that wrap this:

```bash
kubectl exec -n application-nonprod <head-pod> -- \
  bash /opt/slime/scripts/<training-script>.sh
```

### List Ray jobs

```bash
kubectl exec -n application-nonprod <head-pod> -- ray job list
```

### Check job status

```bash
kubectl exec -n application-nonprod <head-pod> -- ray job status <submission_id>
```

### View job logs

```bash
# Follow logs in real time
kubectl exec -n application-nonprod <head-pod> -- ray job logs <submission_id> --follow

# If ray job logs are empty or lagging, check worker logs directly
kubectl exec -n application-nonprod <head-pod> -- \
  tail -100 /tmp/ray/session_latest/logs/worker-*.err
```

### Stop a Ray job

```bash
kubectl exec -n application-nonprod <head-pod> -- ray job stop <submission_id>
```

**Never use `pkill python` on pods** -- it kills the pod process itself. Always use `ray job stop`.

### Delete a job (terminate all pods)

To fully terminate a job and all its pods, delete the Volcano job (vcjob):

```bash
kubectl delete vcjob <vcjob-name> -n application-nonprod
```

The vcjob name is the pod name with the `-startraycluster-{N}-0` (or `-convertckpttohf-{N}-0`, etc.) suffix stripped. For example:
- Pod: `shuowei-qrouter-test-g4mmnd76c1gvgd-startraycluster-4-0`
- vcjob: `shuowei-qrouter-test-g4mmnd76c1gvgd`

This deletes **all pods** in that job (all nodes in the cluster).

To find your vcjob names:

```bash
kubectl get vcjob -n application-nonprod | grep shuowei
```

## Shared Filesystem

`/shared` is a bind-mounted shared filesystem accessible from all pods. **Never delete anything in `/shared`** -- it's shared across users.

### User workspace

Each user has a workspace at `/shared/dev/<username>/`. For the current user:

- **Experiments/checkpoints**: `/shared/dev/shuowei/exp/`
- **General workspace**: `/shared/dev/shuowei/`

### Common shared paths

| Path | Contents |
|------|----------|
| `/shared/models/` | Pre-downloaded model weights |
| `/shared/dev/<user>/exp/` | Experiment checkpoints and outputs |
| `/shared/dev/luqn/data/` | Shared training/eval datasets |

### Code paths inside pods

| Path | Description |
|------|-------------|
| `/opt/slime/` | Project code (copied during image build, overridable via kubectl cp) |
| `/root/Megatron-LM/` | Megatron-LM installation |
| `/sgl-workspace/sglang/` | SGLang dev build |

## S3 Backup and Sync

Checkpoints and data are automatically backed up to S3 at `s3://p11-dev/`. The S3 path mirrors the shared filesystem path (minus `/shared/dev/`).

### S3 bucket structure

| Shared FS path | S3 path |
|---|---|
| `/shared/dev/shuowei/niletron/exp/<exp>/iter_XXXX/` | `s3://p11-dev/shuowei/niletron/exp/<exp>/iter_XXXX/` |
| `/shared/dev/luqn/checkpoints/<model>/` | `s3://p11-dev/luqn/checkpoints/<model>/` |

### Sync from S3 back to /shared (restore deleted checkpoints)

Requires AWS credentials with `p11` profile. Must be run from a pod (or a machine with access to `/shared`).

```bash
# 1. Install awscli on the pod if needed
pip install awscli -q

# 2. Copy AWS credentials to the pod
kubectl exec -n application-nonprod <pod> -- mkdir -p /root/.aws
kubectl cp ~/.aws/credentials <pod>:/root/.aws/credentials -n application-nonprod
kubectl cp ~/.aws/config <pod>:/root/.aws/config -n application-nonprod

# 3. Sync a checkpoint from S3 to /shared
kubectl exec -n application-nonprod <pod> -- bash -c '
AWS_PROFILE=p11 aws s3 cp \
  s3://p11-dev/<user>/path/to/iter_XXXX/ \
  /shared/dev/<user>/path/to/iter_XXXX/ \
  --recursive
'
```

### Example: Restore a Megatron checkpoint

```bash
# Full checkpoint (~398 GiB for Qwen3-30B, takes ~25 min at 265 MB/s)
AWS_PROFILE=p11 aws s3 cp \
  s3://p11-dev/shuowei/niletron/exp/qwen3-30B-sft2999-rlvr1-async-4awo8pow/iter_0000199/ \
  /shared/dev/shuowei/niletron/exp/qwen3-30B-sft2999-rlvr1-async-4awo8pow/iter_0000199/ \
  --recursive
```

### Example: Restore an HF checkpoint

```bash
# HF checkpoint (~57 GiB, takes ~4 min)
AWS_PROFILE=p11 aws s3 cp \
  s3://p11-dev/luqn/checkpoints/Qwen3-30B-A3B-Base-cp4-16h_slime-nemo-v2-rerun/iter_0002999_hf/ \
  /shared/dev/luqn/checkpoints/Qwen3-30B-A3B-Base-cp4-16h_slime-nemo-v2-rerun/iter_0002999_hf/ \
  --recursive
```

### List available checkpoints on S3

```bash
AWS_PROFILE=p11 aws s3 ls s3://p11-dev/shuowei/niletron/exp/<exp-name>/
```

## Continuing a Stopped Experiment

To resume training from a checkpoint:

1. Set `--num-rollout` to the **new total** (not the additional count)
2. Add `--override-opt-param-scheduler` to reset the LR scheduler
3. Ensure `--load` and `--save` point to the checkpoint directory

Example: if original ran 200 rollouts and you want 400 total:
```bash
--num-rollout 400 --override-opt-param-scheduler
```

## Common Issues

### ECR push "not authorized"

Refresh both credential profiles and make sure `AWS_PROFILE=p11` is exported before ECR login. See the Authentication section above.

### kubectl commands fail with auth errors

Run `bash ~/verify.sh` to refresh all credentials.

### Ray job logs are empty or delayed

Ray's log aggregation can lag. Check worker logs directly on the head pod:
```bash
kubectl exec -n application-nonprod <head-pod> -- \
  ls -lt /tmp/ray/session_latest/logs/worker-*.err | head -5
kubectl exec -n application-nonprod <head-pod> -- \
  tail -100 /tmp/ray/session_latest/logs/worker-*.err
```

### kubectl cp fails with "filespec must match the canonical format"

Write full pod names directly in the command. Shell variable interpolation can cause issues with the colon-separated `pod:path` format.
